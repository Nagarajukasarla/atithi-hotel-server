# Database Migration Guide: Local to Neon Cloud

This guide provides steps and commands to migrate your local PostgreSQL database (`atithi_hotel`) to your Neon cloud database.

The local database credentials were read from [application.yaml](file:///d:/resource/Projects/Hotel%20Management/atithi-server/src/main/resources/application.yaml):
* **Host**: `localhost`
* **Port**: `5432`
* **Username**: `postgres`
* **Database Name**: `atithi_hotel`
* **Password**: `root`

---

## 1. Generated Backup Files
We have already successfully generated two formats of your database backup in this folder:
1. [`atithi_backup.sql`](file:///d:/resource/Projects/Hotel%20Management/atithi-server/src/main/resources/db/atithi_backup.sql): Plain SQL script (schema + data), human-readable. Can be viewed and executed inside any SQL IDE/query tool.
2. [`atithi_backup.dump`](file:///d:/resource/Projects/Hotel%20Management/atithi-server/src/main/resources/db/atithi_backup.dump): Compressed custom binary archive. This is the recommended format for CLI restore because it is faster, compressed, and handles schema definitions more robustly.

If you ever need to regenerate these backups locally, you can use the commands below.

### Commands Used to Create Backups (Windows PowerShell)

* **For Custom Binary Dump (`.dump`):**
  ```powershell
  $env:PGPASSWORD="root"; pg_dump -h localhost -p 5432 -U postgres -d atithi_hotel -F c -f atithi_backup.dump
  ```

* **For Plain Text SQL (`.sql`):**
  ```powershell
  $env:PGPASSWORD="root"; pg_dump -h localhost -p 5432 -U postgres -d atithi_hotel -F p -f atithi_backup.sql
  ```

> [!NOTE]  
> In Windows PowerShell, environment variables are set using `$env:VAR_NAME="value"`. In standard Windows Command Prompt (CMD), use `set PGPASSWORD=root` before running `pg_dump`.

## 2. Restoring to Neon Cloud Database

You can restore your database using either the **Connection URI** (simplest and recommended for Neon) or via **individual connection parameters**. 

Replace `USER`, `PASSWORD`, `HOST`, and `DBNAME` with your actual Neon database credentials (which you can copy from your Neon Console dashboard).

### Option A: Using Connection URI (Recommended)
Neon provides a single-line connection string. This is the cleanest way to run the CLI tools because it automatically handles SSL requirements.

* **Restore using Custom Binary Backup (`atithi_backup.dump` - Recommended):**
  ```powershell
  pg_restore --no-owner --no-privileges -d "postgresql://USER:PASSWORD@HOST/DBNAME?sslmode=require" -F c atithi_backup.dump
  ```

* **Restore using Plain SQL script (`atithi_backup.sql`):**
  ```powershell
  psql "postgresql://USER:PASSWORD@HOST/DBNAME?sslmode=require" -f atithi_backup.sql
  ```

---

### Option B: Using Individual Parameters (Alternative)
If you prefer to connect by specifying host, user, and database separately:

* **Restore using Custom Binary Backup (`atithi_backup.dump`):**
  ```powershell
  $env:PGPASSWORD="YOUR_NEON_PASSWORD"
  pg_restore -h YOUR_NEON_HOST -p 5432 -U YOUR_NEON_USER -d YOUR_NEON_DATABASE --no-owner --no-privileges -F c atithi_backup.dump
  ```

* **Restore using Plain SQL script (`atithi_backup.sql`):**
  ```powershell
  $env:PGPASSWORD="YOUR_NEON_PASSWORD"
  psql -h YOUR_NEON_HOST -p 5432 -U YOUR_NEON_USER -d YOUR_NEON_DATABASE -f atithi_backup.sql
  ```

---

### Option C: Restoring via pgAdmin / SQL IDE
If you want to run the restore using a graphical interface or query editor:
1. Open pgAdmin and connect to your Neon Cloud database.
2. Open a **Query Tool** on your target database.
3. Open the [`atithi_backup.sql`](file:///d:/resource/Projects/Hotel%20Management/atithi-server/src/main/resources/db/atithi_backup.sql) file.
4. Execute the SQL script.

---

> [!TIP]  
> The `--no-owner` (or `-O`) and `--no-privileges` (or `-x`) flags are crucial when restoring to cloud databases. They prevent pg_restore from trying to assign table ownership to your local `postgres` user, avoiding permission errors on Neon.

## 3. Troubleshooting Sequences (Identity Columns)

In modern PostgreSQL (PostgreSQL 10 and newer, including the version used by Neon), tables use the SQL-standard `GENERATED BY DEFAULT AS IDENTITY` instead of the older `SERIAL` type for auto-incrementing primary keys.

### Why Sequences Might "Look" Missing
1. **Implicit Ownership**: When an `IDENTITY` column is used, PostgreSQL automatically creates a sequence behind the scenes (e.g. `amenities_id_seq`). However, this sequence is owned internally by the table column.
2. **GUI Sidebar Visibility**: Because these are table-dependent internal sequences rather than standalone global ones, GUI tools like **pgAdmin** or **DBeaver** often do **not** display them in the top-level `Schema -> Sequences` folder.
3. **Verification**: Even if they are invisible in the sidebar, they are active. Auto-increment will work normally when inserting rows.

### How to Verify Sequences Exist
You can run either of these queries in your Neon SQL editor to confirm the sequences exist:

```sql
-- Query 1: Lists all sequences in the schema
SELECT sequence_schema, sequence_name 
FROM information_schema.sequences;

-- Query 2: Lists all sequence relation objects (including internal identity sequences)
SELECT relname AS sequence_name, pg_get_userbyid(relowner) AS owner
FROM pg_class
WHERE relkind = 'S';
```

### What if the Queries Return Empty?
If the tables exist but no sequences are found, it is likely because **Hibernate's `ddl-auto: update` initialized the tables first** on your cloud database before the restore command ran. 
When the restore command attempts to create tables or define identities on already-existing tables, it will fail silently or throw `already exists` errors, skipping sequence generation.

**To resolve this and perform a clean restore:**
1. **Wipe the Target Cloud DB Schema**:
   Run this in your SQL query editor in pgAdmin for your Neon database to clear the existing tables (ensure you are connected to the correct database!):
   ```sql
   DROP SCHEMA public CASCADE;
   CREATE SCHEMA public;
   ```
2. **Re-run the Restore Command**:
   Execute the restore command (`pg_restore` or `psql`) *before* starting the backend server so the backup is imported onto a clean schema.
